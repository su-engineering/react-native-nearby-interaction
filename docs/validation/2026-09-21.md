## Corrections made during validation

The built-in BLE path supplied every connected peripheral's identifier to
`NINearbyAccessoryConfiguration(accessoryData:bluetoothPeerIdentifier:)`.
Apple's Xcode SDK header documents that this initializer requires a **paired**,
actively connected device implementing the standard NI service and Accessory
Configuration Characteristic. A vendor BLE connection alone is insufficient.
The T-TAG path now uses `NINearbyAccessoryConfiguration(data:)` for foreground
ranging. External mode retains the explicitly supplied peer identifier; its
requirements are documented in the README.

The example now includes timestamped state/disconnection logs and measurement
samples at most once per second, and uses the display name Nearby Interaction.
It also uses dynamic iOS system colors. Before this correction, dark mode rendered
black text against a black root view: native measurements reached JavaScript and
the hook snapshot, but the user could not see the distance or session log. This
was reproduced in the simulator and visually verified after correction. The
maintainer confirmed that the distance became visible on the iPhone.

The `--diagnostics` example launch argument forwards React Native logs to stderr
and disables the idle timer for that process. The Ruby build harness explicitly
includes `nkf`.

The initial local archive check was blocked by sandbox access to the default
npm cache. It passed using a writable cache; no npm cache ownership changes
were needed. The initial developer-image mount failed because the iPhone was
locked. Mounting succeeded after the maintainer unlocked and connected it.
The first installation used a cached provisioning profile for another device;
signing in to Xcode and rebuilding for the actual iPhone resolved installation.

## Hardware observations

Temporary instrumentation was added only to the installed test copy to compare
native callbacks, generated JavaScript events and the React snapshot. No event
delivery defect was found. Native BLE/NI debug logging is excluded from the
library sources and release archive.

- Native trace: scanning → connecting → configuring → ranging.
- Two captured sessions contained 938 and 731 native measurement events,
  respectively, with distances spanning approximately 0.15–1.95 m overall.
  These are observed readings, not calibrated accuracy measurements.
- JavaScript received the measurements and the React snapshot updated with
  matching values. Missing direction and horizontal angle remained null.
- Maintainer confirmed visible changing distances after the dark-mode fix.
- Maintainer confirmed Home Screen → app resume restored ranging.
- Explicit Stop cleared the reading; starting again restored ranging (maintainer
  confirmation and native trace).
- Power-cycling the T-TAG cleared the reading and restored ranging. The trace
  showed `BLE_DISCONNECTED`, a recoverable error, reconnecting, fresh negotiation
  and ranging; the maintainer confirmed the displayed result.
- Final clean build: all temporary native/JavaScript instrumentation was removed
  from the installed package, the app was rebuilt and reinstalled, and normal
  example logs recorded live distance measurements again. The maintainer
  confirmed that the clean build displayed the distance.

For the regular 0.1.0 release, the manifest, lockfiles, documentation and release
workflow were updated without changing runtime code. Seven additional release
script tests cover `latest` versus `next`, GitHub prerelease flags and refusal to
publish a private repository, modified archive or already-published version.
The resulting 23-test suite, strict checking, codegen and archive check passed.

## Remaining acceptance

This establishes initial distance ranging and basic recovery on one device/tag
combination. Permission denial, Bluetooth-off behavior, long-range/out-of-range
accuracy, invalid firmware/configuration, chunking, multiple tags, external
transports, other device/OS versions and actual direction/angle measurements
remain unverified on hardware. The firmware revision should be recorded in a
future validation run. The regular 0.1.0 release retains these limitations.
